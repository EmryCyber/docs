---
title: "API Keys"
description: "Create scoped API keys for ticket reads, updates, assignment, history, notes, time and directory access."
---

API keys let an external automation — an n8n workflow, a Zapier zap, a custom script — read or write the data its scopes allow. Paired with [outbound webhooks](/settings/webhooks), this closes the loop: a webhook tells your automation something happened, and an API key lets it read context or write the result back.

<Note>
  API keys require PSA access and explicit scopes. They do not inherit your full account permissions. See the [Public PSA API](/settings/public-api) for endpoint, scope, pagination and update details, or the [OpenAPI document](https://app.regentra.io/api/v1/openapi.json) for the machine-readable contract.
</Note>

## Creating a key

<Steps>
  <Step title="Open API Keys settings">
    Go to **Settings → API Keys** and click **New Key**.
  </Step>
  <Step title="Name it">
    Give the key a name that identifies what will use it (e.g. "n8n — ticket automations").
  </Step>
  <Step title="Choose scopes">
    Select the permissions this key needs:
    - **Time entries** — create time entries on tickets.
    - **Internal notes** — add internal notes to tickets.
    - **Read tickets**, **List tickets**, **Update tickets**, **Assign tickets**, and **Read ticket history** — separate permissions for each operation.
    - **Read time entries** and **Read technicians, groups, companies and contacts** — broader reporting and directory access.
    - **Time entries for a named technician** — additionally permits time attribution to a person; requires Time entries too.
  </Step>
  <Step title="Set an expiration (optional)">
    Set an expiration date, or leave it open-ended.
  </Step>
  <Step title="Save and copy the key">
    Regentra shows the full key exactly once. Copy it now — it can't be retrieved again, only revoked and replaced with a new one.
  </Step>
</Steps>

## Using a key

Every key starts with `rgk_`. Send it as a bearer token on every request:

```
Authorization: Bearer rgk_1a2b3c4d5e6f...
```

### Confirming a key works

`GET /api/v1/ping` requires no scope and has no side effects — use it to confirm your Authorization header is wired up correctly before pointing a real workflow at the write endpoints:

```bash
curl https://app.regentra.io/api/v1/ping \
  -H "Authorization: Bearer rgk_..."
```

```json
{
  "ok": true,
  "organizationId": "org_...",
  "keyName": "n8n — ticket automations",
  "scopes": ["tickets:note:write", "tickets:time:write"]
}
```

### Adding an internal note to a ticket

Requires the **Internal notes** scope.

```bash
curl -X POST https://app.regentra.io/api/v1/tickets/{ticketId}/notes \
  -H "Authorization: Bearer rgk_..." \
  -H "Content-Type: application/json" \
  -d '{ "message": "Escalated to vendor support, ticket #48213 opened on their side." }'
```

```json
{
  "note": {
    "id": "cku9x...",
    "createdAt": "2026-09-05T18:02:11.000Z"
  }
}
```

Notes created through the API are always internal — visible to your team only, never to the customer, and they never trigger a customer-facing email.

### Logging time on a ticket

Requires the **Time entries** scope.

```bash
curl -X POST https://app.regentra.io/api/v1/tickets/{ticketId}/time-entries \
  -H "Authorization: Bearer rgk_..." \
  -H "Content-Type: application/json" \
  -d '{
    "minutes": 45,
    "description": "Investigated and resolved DNS propagation delay",
    "billable": true
  }'
```

```json
{
  "entry": {
    "id": "ckt7z...",
    "minutes": 45,
    "workDate": "2026-09-05T00:00:00.000Z",
    "status": "SUBMITTED",
    "billable": true,
    "hourlyRate": 150,
    "userId": "cku2a..."
  },
  "agreementSource": "company_default"
}
```

Time entries created this way land in the same **Submitted** approval queue as time logged in the app — an admin still reviews them before they're billable. The hourly rate is always resolved automatically from the ticket's company agreement (or your org's default rate); you can't set a rate on the request itself.

By default, time is credited to your organization's automation service account, which does not consume a billable PSA seat. To credit a specific technician, a new key also needs **Time entries for a named technician**; add `userEmail` matching an active, non-service technician in your organization. Older keys retain their pre-existing attribution behavior. Invalid technician choices are rejected rather than silently attributed elsewhere.

### Idempotent requests

Automations retry. To make a retried request safe, send an `Idempotency-Key` header on time-entry creation:

```bash
curl -X POST https://app.regentra.io/api/v1/tickets/{ticketId}/time-entries \
  -H "Authorization: Bearer rgk_..." \
  -H "Idempotency-Key: n8n-run-48213-step-3" \
  -H "Content-Type: application/json" \
  -d '{ "minutes": 45, "description": "..." }'
```

If a request with the same key already created an entry for your organization, Regentra returns that existing entry instead of creating a duplicate, with `"idempotentReplay": true` in the response.

## Attribution

Every write made through an API key is audit-logged and attributed to the key, not to a person — audit log entries show the key's name so you can trace exactly which automation made a change.

## Editing scopes

Use **Edit key** to change permissions without generating a new secret. New scopes are never granted to existing keys automatically. Creating a key or adding permissions can require a recent identity check; complete it and return to the action.

## Revoking a key

Click **Revoke** on any key from **Settings → API Keys**. A revoked key stops working immediately. This can't be undone — create a new key if the automation needs to keep running.

## Errors

Missing, malformed, unknown, revoked or expired credentials return `401 Unauthorized`. Once a key is recognized, missing scope returns `403 insufficient_scope` with the required permission. Product and inactive-subscription refusals also return a specific `403`. Check the key's status and scopes in Regentra when troubleshooting.

Requests are rate-limited and can return `429 Too Many Requests`. Read and write budgets are separate; see [API limits](/settings/public-api#limits-and-failures). Request bodies are capped at 1 MiB. New note/time keys receive readable validation errors with machine codes and field details; older keys keep their legacy validation format.
