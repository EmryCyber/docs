Notification rules let you decide who gets emailed when something happens in the PSA — without writing automation rules. The engine is purpose-built for ticket events, runs server-side, and routes to a list of recipient emails per rule.

<Note>
  This page covers **Notification Rules**, which route events to a recipient list. Personal email, sound and desktop preferences live in **My account → Notifications**. Custom rules and platform-default notifications have different delivery controls; an explicit rule can notify its chosen recipients even when they have disabled a corresponding platform email.
</Note>

## What it does

- **Personal and team rules** — any user can create a rule for themselves; admins can additionally create "team" rules that route to other org users and free-text email addresses (a tech's own rule can only ever email the tech themself)
- **Ticket-spike detection** — a built-in detector that fires when a portal company hits 5+ new tickets, or 3+ new tickets in the same category, within a 10-minute window
- **Filterable triggers** — match on ticket priority (one value), category (exact text match), a specific client, and/or "only when assigned to me"
- **Recipient cap** — up to 25 org-user recipients and 25 free-text email addresses per rule (defense against accidentally CC-ing the entire org)
- **Quiet hours and cooldown** — suppress a rule during a configured time window (with a priority bypass list), and throttle repeat emails to the same recipient
- **Org-scoped** — rules are tenant-scoped at the API layer; an MSP cannot receive a notification for another MSP's tickets

## How to create a rule

<Steps>
  <Step title="Open the rules page">
    Navigate to **Settings → Notification Preferences**, then click the **Notification Rules** card near the top of the page.
  </Step>
  <Step title="Click New Rule">
    Enter a descriptive name (e.g., "Critical tickets for Acme Health → on-call inbox").
  </Step>
  <Step title="Choose the trigger event(s)">
    Check as many as you want:
    - **New ticket** — fires on new ticket from any source
    - **Status changed** — fires on every status transition
    - **Reply added** — fires on every customer-visible reply
    - **Ticket spike** — the built-in spike detector (see below)
    - **SLA warning** — fires when a ticket's SLA timer enters the at-risk window before breach
    - **Escalated** — fires when an automation rule or operator moves a ticket to ESCALATED status
    - **Ticket waiting in a group** — a ticket is left unassigned in a technician group
  </Step>
  <Step title="Add filters (optional but recommended)">
    - **Client** — narrow to one portal company, or leave as "Any client"
    - **Priority** — one of LOW / MEDIUM / HIGH / CRITICAL, or "Any priority"
    - **Category** — match an exact category string
    - **Only fire when the ticket is assigned to me** — a checkbox, not a technician picker
    - **Only fire when the ticket is part of a spike** — a checkbox, independent of the "Ticket spike" trigger above
    - **Technician group** or **Only fire for my groups** — limit the rule to group queues you want to monitor

    All filters AND together: the rule fires only when every filter you set matches.
  </Step>
  <Step title="Add recipients (optional)">
    Leave this blank to email only yourself. Admins can additionally add other org users, group members and comma-separated extra email addresses (e.g., `oncall@msp.com`) — non-admins can only route a rule to themselves.
  </Step>
  <Step title="Set quiet hours and cooldown (optional)">
    Quiet hours suppress the rule during a from/to time window in your organization's timezone, unless the ticket's priority is on the bypass list you check. Cooldown sets a minimum number of seconds between two emails to the same recipient from this rule (default 60).
  </Step>
  <Step title="Save">
    New rules are active immediately — there's no separate "Enabled" toggle to flip on creation; use the **Power** icon on an existing rule to pause or resume it later.
  </Step>
</Steps>

## Priority filters

The Priority filter matches the ticket priority carried by the event. Customers describe urgency rather than setting Critical; technicians control final impact and priority. The AI analyzer's suggestion does not apply itself. See [Automations & AI](/psa/automations-and-ai#ai-and-ticket-priority).

## Bell and unanswered work

The bell retains unread assignments, mentions, replies and new-ticket notifications rather than using only a count of unseen tickets. Reading an alert updates its unread state without resolving the underlying ticket, policy comment or SLA breach.

For customer work that nobody has picked up, configure [Unanswered tickets](/settings/tickets#unanswered-ticket-alerts). For queue-specific alerts, create a Ticket waiting in a group rule; group creation alone does not turn that rule on.

## Ticket-spike detection

A spike fires when a portal company crosses either of two independent thresholds within a rolling 10-minute window: 5 or more new tickets total, or 3 or more new tickets sharing the same category. Either one fires the **Ticket spike** trigger. Useful for catching site-wide outages early — one rule with this trigger and your on-call inbox covers every customer.

The spike detector runs as part of the same background pipeline that processes new tickets, so the alert email lands within seconds of the ticket that crosses the threshold.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Can a notification rule write to a ticket (e.g., change assignee)?">
    No. Notification rules only send emails. For state-changing automations (assign / change priority / set status), use [PSA → Automations](/psa/automations-and-ai) — that engine is separate.
  </Accordion>
  <Accordion title="What if I don't add any recipients?">
    The rule defaults to emailing just you, the rule's owner — this is the normal case for a personal rule. You only need the recipients field for a team rule that should also reach other people.
  </Accordion>
  <Accordion title="How do I stop a rule temporarily?">
    Click the power icon on the rule in the rules list to disable it. The rule is preserved but won't fire until you re-enable it the same way.
  </Accordion>
  <Accordion title="Are recipients deduplicated across rules?">
    Yes. Within an event's rule-dispatch run, a recipient reached by an earlier matching rule is not sent another rule email for the same event. Custom rules run oldest first, followed by the platform-default rule. An address repeated within a rule is also deduplicated. Separate events can still produce separate notifications.
  </Accordion>
  <Accordion title="Can I scope a rule to my MSP-managed clients only?">
    Yes — set the Client filter to one specific client, or create one rule per client. Notification rules are tenant-scoped at the API layer; you cannot accidentally route another MSP's tickets to your inbox.
  </Accordion>
</AccordionGroup>
